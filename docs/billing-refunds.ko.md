# 결제·환불 구현 현황과 운영 기준

이슈: #132. 이 문서는 1차 서버 기반 구현 기록이며, 인앱결제 출시 완료를 의미하지 않습니다.

## 현재 완료 범위

- [x] 구매별 구독 권한 및 상담 이용권 원장
- [x] 스토어·환경·갱신 회차별 거래 ID 유일성
- [x] 구매별 이벤트 ID 중복 처리, 동일 ID의 다른 본문 거절
- [x] 낮거나 같은 revision의 결과는 STALE로 보관하고 권한 변경 제외
- [x] 구독 자동 갱신 해지와 이용 권한 종료 분리
- [x] 유효한 다른 구독이 있으면 해당 권한 보존
- [x] 구매 lot별 이용권 예약·성공 차감·실패 해제
- [x] 환불 취소 시 이전에 사용한 이용권 재지급 방지
- [x] 완료 AI 사용량·암호화 응답의 실패 덮어쓰기 방지
- [x] 실패 확정된 AI 요청의 뒤늦은 성공 차단
- [x] 캐시 저장 실패가 완료 응답 반환을 방해하지 않도록 보강
- [x] 실패 응답의 실제 API 비용 보존, 임베딩 비용 중복 합산 수정

**아직 연결하지 않은 부분:** Apple/Google 검증, webhook 수신, 앱 구매/환불/복원 UI, AI 유료 세션 과금 연결, 관리자 화면, 정산. 새 원장은 내부 서비스이며 외부 지급 API가 없습니다. 기존 `users.subscription_tier` 기반 AI 정책은 바꾸지 않았습니다. 실제 유료 결제를 켜면 안 됩니다.

## 핵심 정책

### 취소·환불·회수 구분

`autoRenew=false`는 다음 갱신 중단입니다. 유효기간이 남아 있으면 접근을 유지합니다. 금전 상태(`PAID`, `PARTIALLY_REFUNDED`, `REFUNDED`)와 `accessRevoked`는 별개입니다. 환불 알림 이름만으로 사용자 전체 등급을 FREE로 바꾸지 않습니다.

Apple의 환불 취소(`REFUND_REVERSED`)도 새 검증 결과로 반영해야 합니다. Google RTDN만으로는 완전한 상태를 알 수 없으므로 Developer API 조회가 필요합니다. [Apple 알림 종류](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype), [Google RTDN](https://developer.android.com/google/play/billing/rtdn-reference)

### 이용권

- 구매당 허용 총량에서 `RESERVED`, `COMPLETED` 수를 뺀 용량만 예약할 수 있습니다.
- 동일 사용자·sessionId는 한 번만 생성합니다. 후속 질문마다 새 예약을 만들지 않습니다.
- 같은 sessionId의 종료 상태를 반환하면 호출자는 AI를 다시 생성하지 않아야 합니다.
- 실패는 RESERVED만 RELEASED로 바꿉니다. 이미 COMPLETED라면 복원하지 않습니다.
- 부분 환불로 총량이 줄면 해당 구매의 진행 중 예약을 해제합니다. 다른 구매 예약은 건드리지 않습니다.
- 이미 소비한 수량이 허용 총량보다 많아져도 지갑 전체를 음수로 만들거나 다른 구매에서 회수하지 않습니다.
- 환불 취소는 허용 총량만 복구합니다. 기존 COMPLETED 기록이 남아 재지급되지 않습니다.
- 월/연 구독자의 이용권 미차감 정책과 최대 3회 후속질문 세션은 다음 유료 AI 연결 단계에서 구현합니다.

### AI 성공 확정

`PENDING -> COMPLETED 또는 FAILED`만 허용합니다. 완료 기록과 암호화 응답은 같은 트랜잭션으로 저장합니다. 전송 실패 이후에도 완료된 응답은 기존 clientRequestId로 재조회할 수 있습니다. 캐시 저장은 이후에 실행하며 오류가 나도 저장한 답변을 취소하지 않습니다.

기존 Redis 어댑터도 쓰기 오류를 흡수하고 있었습니다. 이번 수정은 특정 운영 캐시 장애가 있었다는 진단이 아니라, application/원장에서도 최종 상태를 보장하는 추가 방어입니다.

유료 AI 연결 시 `completeCredit()`와 최종 답변 저장은 반드시 동일 DB 트랜잭션에서 실행해야 합니다. 외부 AI 호출 동안 DB 잠금을 유지하지 않습니다. 예약 만료 작업과 늦은 완료 경합, 처리 중 앱 종료, 재전송, 응답 보관기간 만료도 연결 테스트가 필요합니다. **현재 유료 이용권을 AI 호출이 자동 소비하는 것은 아닙니다.**

## 동시성과 장애

- 동일 사용자 행을 먼저 잠가 예약과 환불을 직렬화합니다. 서로 다른 사용자의 요청은 별도 행을 사용합니다.
- 구매 자연키와 사용자·sessionId DB 유일 제약이 최종 방어입니다. Redis lock에 의존하지 않습니다.
- 동일 거래를 다른 계정에 등록하면 거절합니다. 서로 다른 계정의 최초 등록 경합은 DB unique 위반으로 트랜잭션 전체가 롤백됩니다.
- 이벤트 저장 실패도 구매 상태 및 예약 변경과 함께 롤백됩니다.
- 일반적인 상담 세션 수에서는 사용자별 짧은 행 잠금이 단순합니다. 장기적으로 사용 이력이 커지면 구매 lot별 예약/완료 카운터와 잠금 단위를 검토합니다.
- 탈퇴 계정은 신규 권한과 이용권 예약을 받지 않지만 기존 구매의 환불 상태 갱신은 허용합니다. 원장에는 이메일·상담 원문·purchaseToken이 없습니다. 가명 사용자 ID 및 거래 ID도 개인정보 관리 대상이므로 보존/파기 정책 확정 없이 실제 데이터를 적재하지 않습니다.

## 다음 구현 순서와 출시 차단 조건

1. **스토어 검증 및 durable inbox**
   - Apple 서명/인증서 체인/bundleId/environment/appAppleId 검증. Google Pub/Sub OIDC audience/서비스 계정 검증 후 Developer API 조회.
   - 상품 allowlist, appAccountToken/obfuscatedAccountId로 구매 소유권 확인. Google 갱신마다 달라지는 주문 회차 ID와 purchaseToken을 구분.
   - inbox DB 저장 성공 후에만 2xx. 중복, 재시도, 역순, 유실 보정, dead letter 처리.
   - `VerifiedPurchaseSnapshot`은 서명 검증기가 아니라 내부 입력 모델입니다. 클라이언트 JSON을 직접 변환하는 webhook/controller를 만들지 않습니다.
   - 구매별 조회 작업을 직렬화하고 조회 시작 전에 revision을 예약해 결과 순서를 관리합니다. 알림 수신 시각이나 조회 완료 시각을 스토어 순서로 간주하지 않습니다. 같은 이벤트 재처리는 최초 검증 결과와 revision을 재사용해야 합니다.
   - 구독 그룹/연결 purchaseToken 교체, 업그레이드로 대체된 이전 거래도 재조회·회수해야 이전 권한이 남지 않습니다.
   - 환불/복원 시점에 실제 구독과 AI 권한을 DB에서 계산하도록 resolver 연결. JWT의 과거 PREMIUM 값만 신뢰하지 않기.
2. **유료 AI 세션 연결**
   - 세션 생성/추가질문/최종완료 상태, 예약 소유권, 실패/만료 복원, 성공 결과 재전달.
   - 구독과 별도 이용권의 중첩 정책, 스트리밍 중단, 안전 안내 응답의 비과금, 부적절한 출력 비과금 검증.
3. **앱 UI**: 상품 가격 조회, 구매/복원, 이용권 잔량, 구독 관리, 스토어 환불 요청 안내, 지원 문의.
4. **관리자**: 거래 조회, 검증 상태 재동기화, 처리자/사유 감사 로그. 프리미엄 수동 토글 대신 근거 있는 복구.
5. **악용 검토**: 반복 패턴을 검토 대상으로 표시. 정상 환불을 이유로 자동 영구차단하지 않음. 상담 원문을 증빙에 포함하지 않음.
6. **정산/알림**: 통화별 실제 정산자료 대사, 환불/회수 불일치, inbox 지연, 예약 정체, 보존기간 관리.

고객 안내는 'N시간 이후 무조건 불가'로 고정하지 않습니다. 구매처 환불 절차와 관계 법령상 권리를 안내하고, 장애에 따른 이용권 복원은 스토어의 금전 환불과 구분합니다. 최종 약관은 출시 시점의 정책 및 법률 검토가 필요합니다.

## 검증 방법

일반 회귀: `./gradlew test --no-daemon` (실제 OpenAI 결제 호출 제외).

PostgreSQL: `./gradlew billingPostgresTest --no-daemon`.

후자는 **폐기 가능한 로컬** `127.0.0.1:55439/mypasture_billing_test` DB, `billing_test` 사용자/`billing_test_only` 테스트 암호만 대상으로 합니다. Hibernate create-drop이므로 기존 데이터가 있는 DB를 사용하지 않습니다. CI는 독립 PostgreSQL 16 컨테이너를 사용합니다.

`BillingMigrationPostgresTests`는 독립 스키마의 최소 users 테이블에 V41 baseline 후 V42만 적용합니다. 전체 V1~V41 업그레이드나 운영 데이터 규모의 마이그레이션 검증을 대체하지 않습니다.

## 배포

V42는 기존 테이블 변경 없이 세 테이블을 추가합니다. 자동 권한 지급, 외부 과금 API 호출, 새 고객용 endpoint는 없습니다. main 병합 뒤 기존 워크플로가 staging을 자동 배포하므로 병합 전에 그 영향을 확인합니다. prod 및 스토어 출시는 별도 승인 대상입니다.
