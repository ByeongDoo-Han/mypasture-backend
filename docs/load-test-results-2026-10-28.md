# 로컬 부하 테스트 결과 — 2026-10-28

## 조건

- 대상: `mypasture-load` 전용 Docker Compose의 API 1개, PostgreSQL 1개, Redis 1개. 운영 서비스·운영 DB에는 요청하지 않았습니다.
- API 컨테이너: 2 vCPU·2GiB 제한. PostgreSQL 컨테이너: 2 vCPU 제한. Docker Desktop 전체 할당은 8 CPU·약 7.75GiB였습니다.
- 계정: 실제 로컬 회원가입 API로 준비한 계정 100개, VU마다 다른 액세스 토큰. KOR1910 본문은 로컬 DB에 import됐지만 성경 본문 GET은 부하에 포함하지 않았습니다.
- 읽기 진도: 각 VU가 `GET /api/v1/reading/progress`와 `PUT /api/v1/reading/progress`를 순서대로 호출하고 1초 대기. 단계별 60초 유지.
- AI: `AI_MOCK_ENABLED=true`에서 각 VU가 `POST /api/v1/ai/chat/stream`을 한 번 호출. 100명 실행의 DB 사용 기록 100건은 모두 `COMPLETED`, `cache_hit=false`였습니다.
- QT: 100명이 같은 일회성 모임에 참여. 답변 저장은 VU마다 다른 내용으로 갱신하고 5초 대기. 실시간 구독은 30초 유지했습니다.

## 결과

| 시나리오 | 동시 VU | 기간 | HTTP 요청 | 실패 | HTTP p95 | 처리율 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 읽기 진도 GET+PUT | 30 | 60초 | 3,420 | 0 | 104ms | 56.2 req/s |
| 읽기 진도 GET+PUT | 50 | 60초 | 5,834 | 0 | 52ms | 95.9 req/s |
| 읽기 진도 GET+PUT | 100 | 60초 | 11,546 | 0 | 95ms | 189.0 req/s |
| AI 모의 SSE 완료 | 100 | 1회/인 | 100 | 0 | 4.48초 | 18.2 req/s |
| QT 답변 저장 + SSE 구독 | 저장 50, 구독 100 | 저장 20초, 구독 30초 | 저장 200 | 0 | 저장 1.19초 | 저장 8.7 req/s |

QT 결합 실행에서 구독 100개가 모두 연결됐고 조기 종료는 0건이었습니다. 저장 200건에 대해 구독자 전체에서 `answer-updated` 이벤트 20,000개를 받았으며 100명 모두 업데이트를 받았습니다.

`p95`가 30→50→100명 순으로 일정하게 증가하지 않았습니다. JVM·DB 준비 상태, 로컬 스케줄링, 측정 시간의 영향이 섞이므로 세 수치만으로 확장 효율이나 한계점을 단정하지 않습니다. 오류율 임계값은 1% 미만으로 설정했지만 지연 목표는 아직 제품 SLO로 정하지 않았습니다.

## 해석 범위

이 결과는 **로컬에서 API 처리 경로가 해당 부하를 처리한 기록**입니다. 운영 Cloud Run은 요청 동시성 30과 자동 확장이 적용되고, Cloud SQL의 네트워크·스토리지 지연은 로컬 PostgreSQL과 다릅니다. 성경 본문·검색은 네이티브 기기 SQLite 성능 측정 대상이며 이 결과에 포함되지 않습니다. AI의 4.48초는 모의 응답을 사용한 전체 SSE 시간으로 실제 OpenAI 응답 시간이나 첫 토큰 시간을 뜻하지 않습니다.

실제 사용자의 요청 비율을 확보하면 같은 시나리오를 그 비율에 맞춰 다시 실행하고, 운영과 가까운 별도 환경에서 Cloud Run 인스턴스 수·DB 연결 수·비용을 함께 확인해야 합니다.
