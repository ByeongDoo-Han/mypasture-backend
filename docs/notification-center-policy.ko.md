# 인앱 알림센터 정책

## 목적과 범위

초기 알림센터는 게시된 오늘의 말씀을 앱 안에서 다시 확인하고 해당 화면으로 안전하게 이동하는 기능을 제공합니다. FCM 푸시는 도착을 돕는 운송 수단이며, 알림센터의 원본 데이터는 PostgreSQL입니다.

## 저장 모델

- 모든 사용자에게 같은 알림은 `notification_broadcasts`에 한 번만 저장합니다.
- 사용자가 한 건을 읽으면 `notification_read_receipts`에 사용자와 알림 조합을 저장합니다.
- 전체 읽음은 `notification_read_watermarks`의 시각 한 건으로 처리합니다.
- 오늘의 말씀 게시와 broadcast 생성은 같은 transaction에서 처리합니다.
- `event_key` 유일 제약으로 재시도나 중복 게시 요청이 같은 알림을 두 번 만들지 못하게 합니다.

이 구조는 사용자마다 알림 행을 미리 만드는 방식보다 쓰기 부하와 저장량이 작습니다. 사용자별 제목이나 본문이 필요한 알림은 이후 개인 알림 테이블 또는 별도 대상 테이블로 분리합니다.

## 조회와 보관

- 계정 생성 이전 알림은 노출하지 않습니다.
- 게시 시각과 UUID를 조합한 opaque cursor로 안정적인 다음 페이지를 조회합니다.
- 한 번에 1~50건만 조회할 수 있습니다.
- 초기 broadcast는 게시 후 90일 동안 노출합니다.
- 만료 데이터의 실제 삭제·archive 작업은 운영 보존 기간과 통계 요구를 정한 뒤 별도 batch로 추가합니다.

## 읽음과 동시성

- 단건 읽음에는 `(notification_id, user_id)` 유일 제약을 적용합니다.
- 전체 읽음 watermark를 만들거나 갱신할 때 사용자 행을 잠가 동시 최초 요청을 직렬화합니다.
- 단건 읽음과 전체 읽음은 멱등 요청이며 반복 호출해도 미읽음 수가 음수가 되지 않습니다.

## 이동과 보안

- 서버와 FCM data에는 임의 URL을 넣지 않습니다.
- 모바일은 `DAILY_WORD`와 `TODAY_WORD`처럼 명시적으로 허용한 enum만 화면으로 변환합니다.
- 인증이 필요한 알림을 로그아웃 상태에서 열면 로그인 후 보류한 목적지로 한 번만 이동합니다.
- 푸시 제목과 본문에는 상담, 기도제목, 이메일, token 같은 민감 정보를 넣지 않습니다.

## 운영 지표

- `Provider 접수`는 FCM API가 전송 요청을 수락했다는 뜻이며 실제 기기 도착이나 사용자의 확인을 보장하지 않습니다.
- `앱 열람`은 사용자가 인앱 알림을 읽음 처리한 별도 지표입니다.
- 운영 화면은 `PENDING`, `PROCESSING`, `RETRY_WAIT`, `SENT`, `DEAD`를 분리해 표시합니다.
- 최종 실패 증가는 비활성 token, Firebase/APNs 설정, provider 장애를 순서대로 점검합니다.

## 후속 개선

- 90일이 지난 broadcast와 receipt 정리 batch 및 archive 정책
- 알림 유형별 수신 설정과 quiet hours
- 개인 알림용 대상 모델과 개인정보 보존·삭제 정책
- OpenTelemetry metric과 실패율 경보
- 실제 기기 도착률을 측정할 수 있는 앱 수신 acknowledgement
